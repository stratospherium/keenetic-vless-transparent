# Keenetic × Xray: прозрачный выборочный VLESS-туннель для домашней сети

Полноценная работа с заблокированными сервисами **без VPN-приложений на устройствах**: роутер
на KeeneticOS сам решает, какой трафик отправить через VLESS-туннель, а какой — напрямую.

Проверено на: **Keenetic Ultra (KN-1811), KeeneticOS 5.1.8, Entware (aarch64), Xray 26.x,
VLESS + Reality + XHTTP + постквантовое шифрование (mlkem768x25519plus + mldsa65)**.

## Что умеет

- **Два режима сегментов**: одна Wi-Fi-сеть — весь трафик через туннель, другая — только выбранные
  сервисы (остальное напрямую, без потери скорости).
- **Маршрутизация по доменам** (geosite-справочники + явные домены) **и по IP-диапазонам** —
  работает даже для приложений без SNI (десктопный Telegram) и с зашифрованным SNI/ECH (Instagram).
- **Fail-safe по архитектуре**: правила перенаправления применяются только когда xray жив;
  при падении — сторож снимает их сам, и сеть мгновенно возвращается к прямому маршруту.
  Ошибка конфига не может оставить сегмент без интернета (выводы из реальной аварии — см. ниже).
- Автозапуск после перезагрузки роутера, сторож-цикл, датчик скорости туннеля с журналом.

## Архитектура

```
[Сегмент A: 192.168.1.0/24]  (выборочно)  ─┐
                                           ├─► iptables REDIRECT :1501 ─► Xray ─┐
[Сегмент B: 192.168.2.0/24]  (весь)       ─┘   (маршрутизация: домен/IP)       └─► VLESS/Reality/XHTTP ─► VPS ─► Интернет
```

Решение «прокси или напрямую» принимает Xray по цепочке правил (эшелоны):

1. Домены из geosite-справочников (google, telegram, instagram, facebook, twitter, discord, …)
2. Явные домены, которых нет в справочниках (threads.com, fna.fbcdn.net, …)
3. IP-диапазоны (Google, Meta, Telegram DC, кэши провайдера) — для соединений без SNI
4. Транспортные опции: `sniffing.routeOnly` (маршрутизация по домену без подмены адреса —
   IP-правила продолжают работать при ECH), `xhttp stream-one`, BBR на VPS

### Балансер и резервный канал

Xray держит два исходящих канала до одного VDS-хоста и выбирает живой автоматически:

- `prox-main` — VLESS + XHTTP + Reality + постквант (:443) — основной;
- `prox-reserve` — VLESS + Reality + Vision (:8443) — резерв, другая транспортная логика;
- `routing.balancers` + `leastPing` и `burstObservatory` (пинг обоих каналов раз в минуту) —
  при деградации основного трафик сам переезжает на резерв без ручных действий;
- `routeOnly: false` — xray резолвит домены на стороне VDS, «битые» для домашнего
  DNS адреса перестают влиять на загрузку.

Правила маршрутизации (порядок важен — частное раньше общего): второй сегмент → VDS,
частные сети → напрямую, РФ-домены (category-ru) и geoip:ru → напрямую, кэш провайдера
для заблокированного контента → VDS, известные сервисы → VDS, всё незнакомое зарубежное →
VDS (дефолт-аутбаунд). Блокировки: домены Autodesk → blackhole; шифрованный DNS (DoT:853)
проблемного устройства → REJECT; корпоративный мессенджер и игровые порты → мимо туннеля.

## Установка

> Все шаги выполняются по SSH. Примеры даны для внутренней подсети 192.168.1.0/24.

### 1. Entware на роутере

Компоненты KeeneticOS: `WireGuard VPN`, `Kernel modules for filesystems support`,
`Ext filesystem utilities` (без последнего веб-интерфейс не умеет форматировать в ext4).
Флешка ≥4 ГБ форматируется в ext4 и привязывается к OPKG (страница «OPKG Package Manager»).
Установщик Entware (архив под архитектуру, у KN-1811 — `aarch64-installer.tar.gz`) кладётся в
папку `install/` в корне раздела — роутер развернёт её сам при привязке диска.

SSH Entware: порт **222**, root/keenetic (смените пароль первым делом: `passwd`).

### 2. Xray

Готовый бинарник Xray положить в `/opt/sbin/xray`, dat-файлы (geoip/geosite) — в
`/opt/sbin/` и `/opt/etc/xray/dat/`. Конфиг — `xray/config.example.json` из этого репозитория:

```sh
cp config.example.json /opt/etc/xray/config.json
vi /opt/etc/xray/config.json   # подставить свои значения VLESS-сервера
/opt/sbin/xray -test -c /opt/etc/xray/config.json   # ОБЯЗАТЕЛЬНО: валидация до применения
```

Подставьте: адрес/порт сервера, UUID, encryption, Reality publicKey/shortId/spiderX, mldsa65Verify.
Группы доменов и IP-диапазоны в `routing.rules` — отредактируйте под свой список сервисов.

### 3. Скрипты службы

```sh
cp fw.sh             /opt/etc/xray/fw.sh
cp S99vlessfw        /opt/etc/init.d/S99vlessfw
cp watchdog_loop.sh  /opt/etc/xray/watchdog_loop.sh
cp phone-mon.sh      /opt/etc/xray/phone-mon.sh
cp cron-restart.sh   /opt/etc/xray/cron-restart.sh
cp S01cron           /opt/etc/init.d/S01cron
chmod +x /opt/etc/xray/fw.sh /opt/etc/xray/watchdog_loop.sh /opt/etc/xray/phone-mon.sh \
          /opt/etc/xray/cron-restart.sh /opt/etc/init.d/S99vlessfw /opt/etc/init.d/S01cron
# подсети/исключения настраиваются в начале fw.sh (SEGS, DIRECT_NETS)
/opt/etc/init.d/S99vlessfw start
nohup sh /opt/etc/xray/mon.sh &     # датчик скорости, пишет /opt/var/log/tunnel-mon.log
```

### 4. VPS

Включите BBR — на транзитах с потерями стандартный cubic роняет скорость в ноль:

```
# /etc/sysctl.d/99-bbr.conf
net.core.default_qdisc=fq
net.ipv4.tcp_congestion_control=bbr
```

## Правила эксплуатации

- **Деплой конфига — только через валидацию**: качаете в `config-new.json`, гоняете
  `xray -test`, и лишь при успехе переименовываете и перезапускаете службу. Рабочий конфиг
  никогда не подменяется непроверенным.
- **Диагностика фризов**: лог xray (`/opt/var/log/xray-vless.log`) показывает каждое соединение
  и его маршрут (`-> proxy` / `>> direct`). Замер с трёх точек (клиент · роутер · VPS) +
  корреляция по времени однозначно локализуют проблему. Лог пишется в UTC.
- **Утечка мимо туннеля** выглядит как `>> direct` к знакомому диапазону — закрывается
  добавлением домена или подсети в правила.
- UDP/443 (QUIC) блокируется для сегментов, чтобы браузеры не уходили мимо туннеля —
  приложения откатываются на TCP автоматически.

## Извлечённые уроки (оплаченные аварией)

1. **Откат проектируется до первой правки.** Применение правил перенаправления до проверки,
   что xray запустился, — ошибка, стоившая 30 минут интернета у всей квартиры.
2. Сторож-цикл должен быть **fail-open**: сервис умер → правила сняты, а не наоборот.
3. `sniffing` по умолчанию **подменяет адрес назначения доменом из SNI** — IP-правила перестают
   работать. `routeOnly: true` возвращает им силу (критично для ECH-трафика приложений Meta).
4. Длинные строки (постквантовые ключи >4 КБ) нельзя передавать через SSH-терминал — только файлом.
5. Xray из репозитория XKeen (1.8.4) не понимает XHTTP и постквант — ставьте свежий бинарник.

## Структура

```
xray/config.example.json  — шаблон конфига (плейсхолдеры вместо секретов)
xray/fw.sh                — iptables-правила прозрачного прокси (редирект TCP, блок UDP/443)
xray/S99vlessfw           — init-скрипт: fail-safe запуск xray + правил + сторожа
xray/watchdog.sh          — сторож: xray жив? правила на месте? иначе всё снять/поднять
xray/mon.sh               — датчик скорости туннеля (журнал каждые 10 секунд)
```
